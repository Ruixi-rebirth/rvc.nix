# Contributing

Contributions that improve reproducibility, platform support, or the upstream
RVC experience are welcome.

## Repository layout

```text
flake.nix                Output map: packages, apps, overlay, nixConfig
nix/package.nix          Python environment (uv2nix) and source patching
nix/launcher.nix         Launcher and command wrappers (rvc-realtime, ...)
nix/checks.nix           Every flake check; new checks go here
nix/models.nix           Pinned model assets and their hashes
nix/python-overrides.nix Wheel-specific build/ELF fixes
nix/module.nix           NixOS programs.rvc module
nix/module-test.nix      Module assertions
nix/patches/             Upstream patches, generator, and rule data
nix/tests/               Flake-check test scripts + *-live.sh hardware tests
nix/scripts/             doctor.py and launcher support scripts
python/                  uv workspaces (root = CUDA, python/cpu = CPU)
```

Where to make a change:

| Change                        | File                                     |
| ----------------------------- | ---------------------------------------- |
| Add a package or app variant  | `flake.nix` (`mkVariants`)               |
| Change launcher behaviour     | `nix/launcher.nix`                       |
| Add a flake check             | `nix/checks.nix`                         |
| Change the RVC source patches | `nix/patches/rules.py`, then regenerate  |
| Add or update a model asset   | `nix/models.nix`                         |
| Fix a wheel build/ELF issue   | `nix/python-overrides.nix`               |
| Add a NixOS module option     | `nix/module.nix` + `nix/module-test.nix` |
| Add a Python dependency       | both `pyproject.toml`s + `uv lock`       |

## Style conventions

- File names: Python uses snake_case (`pyproject_sync.py`), shell scripts use
  kebab-case (`realtime-infer-live.sh`), Nix files use kebab-case with a
  single dot (`python-overrides.nix`), and the patch generator assigns
  `NNN-name.patch` prefixes from declaration order.
- Comments: plain sentence comments that say why a thing exists. Structure
  comes from file and function boundaries, not decoration.
- Python tooling (`nix/patches/`, `nix/tests/`, `nix/scripts/`): module
  docstring at the top, data separated from logic, and every substitution or
  assertion annotated with its purpose.

## Before opening a change

```console
nix fmt
nix flake check path:.
nix build path:.#cpu
```

If the change affects CUDA packaging, also run:

```console
nix build path:.#cuda
```

CUDA runtime claims must include the GPU, NVIDIA driver version, and output of
`rvc-doctor`. Redact personal path components before posting that output in a
public issue or pull request. A successful CUDA build alone is not a hardware
runtime test.

## Packaging rules

- Do not run `pip`, create a virtualenv, or download dependencies from a
  launcher.
- Pin source and model downloads by immutable revision and content hash.
- Keep application code and published assets in the Nix store.
- Keep user models, training outputs, logs, and configuration under XDG paths.
- Keep upstream source changes as patch files under `nix/patches/`; do not
  accumulate inline `substituteInPlace` rewrites in `nix/package.nix`.
  Per-file substitution patches are generated by
  `nix/patches/generate_patches.py`; every generated patch starts with its
  purpose, generator, and source of truth, with descriptions beside the rules
  in `rules.py`. Numeric prefixes come from the declaration order in
  `rules.py`; never assign them by hand. A cross-file hand-maintained patch
  must also start with a purpose and maintenance metadata.
  `checks.patches-in-sync` regenerates the patch set from the pinned source
  in CI and fails on any drift.
- Scope Python overrides to the package with the missing build or ELF
  dependency. Do not hide unresolved required libraries.
- Keep CPU as the default output. Hardware-specific acceleration must be
  explicit.
- Keep the CPU and CUDA `pyproject.toml` manifests in sync;
  `checks.pyproject-sync` is the arbiter and documents the allowed exceptions.
- Add or extend a flake check for every regression that can be tested without
  specialized hardware.

## Updating upstream RVC

1. Update only the `rvc-src` input.
2. Regenerate the source patches from that locked input and review the
   resulting diff:

   ```console
   nix flake update rvc-src
   nix run .#generate-patches
   ```

   The generator applies every patch to a clean tree, byte-compares the result
   against the build pipeline, and re-runs the installCheck assertions. Any
   hunk that no longer matches fails here — review whether the change is still
   needed, was adopted upstream, or must be rewritten.

3. Rebuild CPU and CUDA from a clean evaluation.
4. Run the doctor, CLI, WebUI, and realtime smoke checks.
5. Review upstream model-layout and dependency changes before updating model
   hashes or Python locks.

Avoid combining an upstream source update with unrelated package refactoring;
small changes make failures and reviews substantially easier to understand.

Only the exact upstream commit recorded in `flake.lock` is supported. Upstream
updates are deliberate pull requests, not an automatic moving target. A patch
hunk that no longer applies is treated as a required patch review rather than
bypassed.

## Where to start

Good first contributions, no specialized hardware required:

- add or tighten a `checks.*` assertion or extend an existing one
- document a troubleshooting entry in the README
- reduce duplication in the flake outputs or the NixOS module
- improve `nix/patches/generate_patches.py` ergonomics or error messages
- translate documentation into a language you speak

## Release process

1. Run `nix fmt`, `nix flake check path:.`, and build both `.#cpu` and `.#cuda`.
2. Draft release notes for the version and date, create a signed `vX.Y.Z` tag
   from `main`, and publish the notes. Never move an existing release tag.
3. Confirm the release's CI run pushed the CPU and CUDA closures to the
   `ruixi-rebirth` Cachix cache.
